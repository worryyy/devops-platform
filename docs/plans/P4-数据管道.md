# P4 · 数据管道（Kafka + ClickHouse）

> **目标**：Fluent Bit → Kafka → ClickHouse 日志管道跑通；平台日志检索页
  v1；告警/事件数据入 CH；k6 造流量产出管道吞吐/压缩/查询对比数据。
> **工期**：2 周。
> **前置依赖**：P1 验收 A1/A5（集群与 platform ns 就绪）、P3 验收 A1
  （告警链路在流，事件才能双写）。
> **蓝图引用**：§7.3 日志、§7.5 大数据管道、§7.7 压测、§3 资源（Kafka
  node1 ~1G、CH node1 ~2.5G）。
> **状态**：⬜ 未开始

## 1. 任务清单

### 1.1 组件部署
- [ ] `k3s/helm-values/platform/kafka.yaml`：bitnami kafka KRaft 单副本
      （controller+broker 合一），heap ~768M-1G，PVC 20G（保留 72h），
      nodeSelector：控制节点 light 化——按蓝图放 node1（control，
      与构建错峰）需给 node1 同时打 light 标签或用 control；listener
      PLAINTEXT 集群内
- [ ] `k3s/helm-values/platform/clickhouse.yaml`：单副本，
      memory limit ~2.5G，PVC 40G（merge_tree 优化：
      `max_bytes_before_external_sort`/后台 merge 线程按小规格调低），
      nodeSelector control（与构建错峰说明写入 Runbook 备注）
- [ ] `k3s/gitops/applications/platform/{kafka,clickhouse}.yaml`；
      platform-addons destinations 确认覆盖其 namespace（`platform`）
- [ ] 镜像转存 ACR（kafka/clickhouse/choperator 按 postgresql 先例 pin）

### 1.2 采集与入库
- [ ] `k3s/helm-values/platform/fluent-bit.yaml`（或独立 manifest）：
  - input：tail 各节点 `/var/log/containers/*.log`（docker json 解析）
  - 业务日志为结构化 JSON（服务侧 slog JSON 已具备）：parser 提取
    `ts/level/service/route/trace_id/deploy_id/msg`；从 Pod 标签注入
    `service/pod/namespace`（k8s filter）
  - output：Kafka topic `logs.raw`（key=service），batch 512KB/2s
  - 资源 150M，DaemonSet，容忍所有节点
- [ ] ClickHouse 建库表（SQL 入 `platform/server/migrations` 不合适——
  独立放 `monitoring/pipeline/clickhouse/*.sql`，部署时执行）：
  - `kafka engine` 表 `logs_kafka`（topic logs.raw，group platform-sinker）
  - 目标表 `logs(service LowCardinality(String), ts DateTime64(3),
    level LowCardinality(String), route String, trace_id String,
    deploy_id String, pod String, namespace String, msg String,
    attrs JSON, ingestion_ts DateTime DEFAULT now()) ENGINE=MergeTree
    PARTITION BY toMonday(ts) ORDER BY (service, level, ts)
    TTL toDateTime(ts) + INTERVAL 30 DAY`
  - 物化视图 `logs_mv`：logs_kafka → logs（P4 起步用 CH Kafka 引擎；
    Go sinker 为 P4.5 可选演进，见风险）
- [ ] 事件双写：alertgw 落 PG 的同时写 CH `events(kind, source, payload
    JSON, ts)`（alert/发布/巡检事件统一入此表，供周报与 P5 证据包跨域查询）

### 1.3 平台日志页 v1
- [ ] `internal/obs/ch.go`：CH 客户端（clickhouse-go v2），查询构造器
      （白名单字段，防注入）
- [ ] API：
  - `GET /api/logs?service=&start=&end=&level=&q=&trace_id=&limit=200`
    → 时间倒序原始日志
  - `GET /api/logs/patterns?service=&start=&end=&level=`
    → fingerprint 聚合：`regexpReplace(msg, 数字/uuid/引号串, '<x>')`
    取前 120 字符为模板 group by，输出 {pattern, count, first_seen,
    last_seen, pods[], sample}，LIMIT 10
- [ ] 前端 `/logs` 页：过滤栏（服务/级别/时间范围/关键字/trace_id）、
      结果表、模式聚合 tab（条形+样本展开）、时间直方图（CH 按 minute
      count 查询）

### 1.4 k6 造流量与管道压测
- [ ] `benchmarks/k6/` 场景脚本：
  - `baseline.js`：单服务阶梯加压（10→错误率拐点）
  - `daily.js`：13 服务混合读写（读写比 7:3，早晚高峰系数，持续 24h）
  - `jitter.js`：周期性加减压 + 故障注入（延迟/错误），P5 评估素材
- [ ] 管道指标采集：Kafka exporter（lag）接 Prometheus；CH
      `system.parts`/`system.query_log` 关键指标抓取（或经 node exporter
      进程级起步，够用即可）
- [ ] 对比实验（写入 `benchmarks/results/pipeline.md`）：
  管道吞吐（rows/s、Kafka lag 曲线）、CH 写入对查询 P95 的影响
  （压测窗口前后对比）、30 天留存体积与压缩比（`system.parts` bytes
  对比原始日志体积）、日志检索页查询延迟分布

## 4. 风险与回退
| 风险 | 缓解 |
|---|---|
| CH Kafka 引擎在 CH 重启时丢/重消费 | group id 固定 + Kafka 保留 72h；评估 Go sinker（DLQ/重试）为 P4.5 演进 |
| node1 构建与 CH/Kafka 抢内存 | 预算表已留构建错峰；压测窗口禁止触发 Jenkins 构建（写入 k6 脚本注释） |
| bitnami kafka 镜像许可 | 用 bitnamilegacy 转存（postgresql 先例）或换 strimzi |
| 日志非结构化导致解析失败 | 业务侧已 slog JSON；解析失败行落 `service=unparsed` 兜底可观测 |
