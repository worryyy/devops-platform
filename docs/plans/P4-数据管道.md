### 1.2 采集与入库
- [x] `k3s/helm-values/platform/fluent-bit.yaml`（或独立 manifest）：
  - input：tail 各节点 `/var/log/containers/*.log`（docker json 解析）
  - 业务日志为结构化 JSON（服务侧 slog JSON 已具备）：parser 提取
    `ts/level/service/route/trace_id/deploy_id/msg`；从 Pod 标签注入
    `service/pod/namespace`（k8s filter）
  - output：Kafka topic `logs.raw`（key=service），batch 512KB/2s
  - 资源 150M，DaemonSet，容忍所有节点
- [x] ClickHouse 建库表（SQL 入 `platform/server/migrations` 不合适——
  独立放 `monitoring/pipeline/clickhouse/*.sql`，部署时执行）：
  - `kafka engine` 表 `logs_kafka`（topic logs.raw，group platform-sinker）
  - 目标表 `logs(service LowCardinality(String), ts DateTime64(3),
    level LowCardinality(String), route String, trace_id String,
    deploy_id String, pod String, namespace String, msg String,
    attrs JSON, ingestion_ts DateTime DEFAULT now()) ENGINE=MergeTree
    PARTITION BY toMonday(ts) ORDER BY (service, level, ts)
    TTL toDateTime(ts) + INTERVAL 30 DAY`
  - 物化视图 `logs_mv`：logs_kafka → logs（P4 起步用 CH Kafka 引擎；
    Go sinker 为 P4.5 可选演进，见风险）
- [x] 事件双写：alertgw 落 PG 的同时写 CH `events(kind, source, payload
    JSON, ts)`（alert/发布/巡检事件统一入此表，供周报与 P5 证据包跨域查询）

## 5. 执行记录（2026-09-21）

关键实现取舍与踩坑（与计划文本的偏差）：

- **业务日志字段与计划假设不符**：实测 slog 行是 `time/level/caller/msg`
  （无计划假设的 `ts/service/route`）。`logs_mv` 做了三件事适配：
  `ts` 回退 `time`；`service` 从 pod 名正则推导（Deployment/StatefulSet
  命名规则），显式 `service` 字段优先；`level` 归一大写（slog 小写）。
  `route/trace_id/deploy_id` 字段预留（P6 埋点后填充）。
- **fluent-bit Merge_Log 未生效**：k8s filter 配了 `Merge_Log On` 但
  message 内层 JSON 未被提升（fluent-bit 3.2.10 实测）——不依赖它了，
  MV 里做「源切换」：顶层无 `msg` 且 `message` 是合法 JSON 时解析内层。
  修复了 `Kube_Tag_Prefix kube.var.log.containers.`（默认 `kube.` 会导致
  元数据全空——tag 是路径派生的）。
- **CH 侧踩坑**：`JSONAsObject` 要求 JSON 类型列（BAD_ARGUMENTS）→ 改
  `JSONAsString`；config `<merge_tree>` 段写 `background_pool_size`/
  `background_merges_mutations_concurrency_ratio` 在 25.7 直接启动失败
  → lowspec.xml 只留 profiles（外部排序 256M/内存 1.5G/60s 超时）。
- **clickhouse-go v2.48 参数绑定**：native 协议 QueryOptions 走
  `clickhouse.Context(ctx, WithParameters(...))`，`@name` 是 v1 方言、
  直接传 map 会走 legacy bind 报错；时间参数用 epoch 毫秒字符串避开
  会话时区歧义。CH 的正则替换函数是 `replaceRegexpAll`（无 regexpReplace）。
- **kafka-exporter v1.9.0**：flag 是 `--topic.filter`（带点），且
  `--log.enable-sarama=false` 该 build 解析报错，勿加。
- **镜像**：bitnami 主仓已清空（许可变更），从 `bitnamilegacy` 拉
  amd64 转 ACR；fluent-bit/kafka-exporter 同批转存。自建镜像在 arm64
  Mac 上 QEMU 模拟构建会触发 Go 1.26 synctest 崩溃——platform-server
  改本地交叉编译 + distroless 打包（web 正常构建）。
- **部署**：沿用 P3 直推先例（helm template | kubectl apply），Argo app
  定义与 git 一致，出网恢复后自动接管。P4 新增 pod 均显式挂
  `tcr-secret`（default SA 无拉取凭据，fluent-bit/kafka-exporter 踩过）。
- **验收注记**：外部 nip.io 直连实测可达（此前 502 是本机系统代理）；
  patterns 首查 ~5.8s（全表三遍正则），v1 可接受，优化路径留 P7。
